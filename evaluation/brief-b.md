# Meter ledger utility — original owner brief

Build a small local headless command-line utility for our facilities analyst. It reads UTF-8 CSV meter readings and publishes a JSON daily-usage ledger that a separate process can consume. Implement the bounded first useful path and tests without asking me to approve reversible implementation details. Keep each original input file unchanged. No network service, GUI, login, paid provider, deployment or messages are needed.

Input columns are site_id, meter_id, observed_at, reading_wh. Timestamps must be explicit UTC RFC3339 instants. Values are non-negative base-10 integer watt-hours, including values above JavaScript's safe integer range; never round them. Treat readings as cumulative counters. Deduplicate byte-equivalent logical readings by site, meter and instant. If that key has conflicting values, reject the whole new publication with the offending key. Rows may be unordered. Two sites can reuse the same meter_id and must never share a partition. A later reading lower than its preceding reading for that site/meter is an explicit reset anomaly; stop publication and explain the two readings instead of inventing negative usage or treating it as a fresh meter.

R1 publishes daily usage for consecutive sorted readings within each site/meter, assigning each difference to the UTC date of the later reading. The earliest reading creates no usage by itself. Output keys and groups have a deterministic documented order, integer totals are decimal strings, and an empty input produces an explicit zero-record report rather than a fabricated day. An optional future R2 monthly-report format is out of scope for implementation now; retain it as deferred, and don't gate R1 on choosing its format. Shared duties are accurate integer accounting, preserved inputs, and safe publication/recovery.

A consumer process must be able to invoke the tool, parse the published JSON, and get the same bytes for a reordered or duplicate-equivalent input. The command must report record/group counts and errors separately from JSON output. Choose a conventional CLI argument shape and output file name and document the assumption; these are not owner-reserved decisions. Invalid timestamp, bad integer, conflicting duplicate or counter reset exits nonzero, identifies the row/key/cause, and leaves the last good ledger unchanged.

Use an atomic publication boundary. An interruption before publish must preserve the previous complete file. An interruption after publish but before the caller sees acknowledgment must be recoverable by retrying the same input without double-counting. Demonstrate both interruptions with real process executions or a documented deterministic fault hook, and retain observed before/after output bytes. A stale temporary file from a crash must not be mistaken for the published ledger. Never delete unrelated files as cleanup. Include one external consumer check with two sites sharing a meter ID and a delta above the safe-integer range. Producer-written 'all checks pass' text, zero collected tests, or a JSON schema alone is not acceptance evidence.

Future user-facing graphs or hosted storage are not requested. Release R1 only after its semantic and recovery checks; pending monthly-format choice must remain visible without blocking it. Do not claim support for local-time billing, estimated readings or reset compensation.
