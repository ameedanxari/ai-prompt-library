# Native parent workflow

Use this path when the entry point has no configured trusted host and the current native parent can actually observe the user's request, run commands and receive distinct subagent results. A delegated producer or reviewer must not initialize, authorize or register its own host. Read [host integration](../../docs/host-integration.md) for exact commands and trust limits. Missing capabilities stay explicit; do not invent tools, private service access or identities.

1. Inspect the actual user request, existing source inventory and selected run. Reuse an existing valid host and run when resuming. Otherwise retain the exact request and original inputs, with the requested planning stop or implementation authority. Do not add product instructions, rubric hints or previous audit answers to a cold producer request. Before starting, retain the library commit/package, source hashes and host capability observations; these distinguish library output from coordinator intervention.
2. Delegate product planning/implementation to a fresh producer context, identifying its role and the original request/workspace. The producer reads the normal entry point and model. Give it generic host transport only; it may prepare and validate planning while host setup is pending. Record the actual returned native producer ID/context. The parent remains coordinator and does not author its product plan. Use the user's model/quota constraints and available tools; do not fan out merely for count.
3. Initialize the shipped host with a parent-owned profile outside the project. Record actual instruction, producer/context and provenance; never turn planning-only into execution. Provide the producer `HOST-ENVIRONMENT.json` with adapter path and captured instruction metadata so its canonical policy can match the real request. The producer returns review packets, actual observations and paths; it never edits host captures or verifier code.
4. For required review, ask a distinct actual reviewer to read the original sources and the current packet. Compare every relevant original obligation, changed mapping, target lifecycle, delivered/recovery criteria, source constraints and capacity assumptions. For newly authored runs configure independent implementation review; assess the selected work details and relevant forecast and authority context in a separate bound implementation judgment. Scope and detail may be reviewed in one session with separate receipts. Historical runs without the duty have no configured detail review; scope approval does not cover detail. Freeze the selected submitted candidate and its bound context until the actual response is retained and registered; unrelated work can continue only when it leaves that binding unchanged. Preserve stale raw dissent if a race occurs, never rebind a judgment, and obtain a real review of the corrected candidate. Do not seed the expected verdict. Retain the first candidate before feedback and each genuine dissenting result.
5. Check the actual native reviewer result and identity/context, retain raw output, then register the exact capture through `ai-prompt-host`. Pass the unmodified envelope back for canonical `record`. Rejections go to the producer as actual feedback; the producer repairs the cause and produces a fresh bound packet, using `--previous` for conservation review. The parent does not secretly rewrite the plan to achieve a score. Track setup, review, repair and any intervention; report usage only when measured.
6. Once source review and actual instruction verification pass, the producer uses the existing `work-executable` boundary for each bounded item. Within a real implementation request it continues source-consistent reversible work without repeated permission questions. It retains actual command/consumer outputs, including failure and recovery. The parent registers observations it actually witnessed; producer-written positive summaries alone are insufficient. Actual consumer/semantic and applicable design review precede accepting a proof; release has its separate complete-scope and authority judgment.
7. Preserve honest pending inputs at their consumers. Continue other work only when its own executable boundary passes. An explicit plan/review stop ends at that boundary; lack of live access does not authorize a simulated release. A required owner decision, paid action or live operation cannot be inferred from a reasonable technical default.
8. At handoff retain the exact runnable artifact, sources, host captures, judgments, failures, scope/execution status and next action. State what the parent observed versus what the verifier checked. A cold trial measures the shipped workflow including its coordinator/reviewer cost; assisted repair is not first-pass success. Never claim a new host directory or a narrow test proves platform authentication, general autonomy or token savings.

For planning forecasts, retain source-bound milestones, their useful result/recovery and reforecast trigger, disjoint role estimates and typed producer dependencies. Compare capacity only with its explicitly named milestone, release or all-work scope; show unknown estimates and owner waiting separately. Never infer a committed date from labor sums.
