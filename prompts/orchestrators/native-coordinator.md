# Native parent workflow

Use this path when the entry point has no configured trusted host and the current native parent can actually observe the user's request, run commands and receive distinct subagent results. A delegated producer or reviewer must not initialize, authorize or register its own host. Read [host integration](../../docs/host-integration.md) for exact commands and trust limits. Missing capabilities stay explicit; do not invent tools, private service access or identities.

1. Inspect the actual user request, existing source inventory and selected run. Reuse an existing valid host and run when resuming. Otherwise retain the exact request and original inputs, with the requested planning stop or implementation authority. Do not add product instructions, rubric hints or previous audit answers to a cold producer request. Before starting, retain the library commit/package, source hashes and host capability observations; these distinguish library output from coordinator intervention.
2. Delegate product planning/implementation to a fresh producer context, identifying its role and the original request/workspace. The producer reads the normal entry point, model and applicable planning references, inspects available sources and continues the authorized workflow until completion, an explicit stop, or an actual missing input. Give it generic host transport only; it may prepare and validate planning while host setup is pending. Record the actual returned native producer ID/context. The parent remains coordinator and does not author its product plan. Use the user's model/quota constraints and available tools; do not fan out merely for count.
3. Initialize the shipped host with a parent-owned profile outside the project. Record actual instruction, producer/context and provenance; never turn planning-only into execution. Provide the producer `HOST-ENVIRONMENT.json` with adapter path and captured instruction metadata so its canonical policy can match the real request. The producer returns review packets, actual observations and paths; it never edits host captures or verifier code.
4. Prepare the existing distinct scope reviewer before plan exposure for substantial heterogeneous-source, replacement or authority work. This can run alongside the producer and host setup. Give that reviewer only the actual request, unchanged original inventory/authority, applicable library references and authorized access to current repository seams; no canonical plan/views, previous judgments, audit answers, product hints or expected verdict. Do not restrict originals to the producer's mapped requirements. The reviewer retains bounded raw source-located notes on material clauses, accepted/open decisions, current versus reported behavior, plausible wrong implementations, uncertainty and unread/partial material. Check equivalent duplicate formats before sharing inspection. Retain the memo's initial bytes, input hashes and actual context/sequence before exposing the plan. An input-only copy can reduce accidental exposure, but neither a folder nor instructions provide OS isolation. Notes are review provenance, not another requirements model, owner decision, approval envelope or source-complete flag; do not feed them to the producer before its first submission. A note may be corrected with an explicit source-based reason, and a missed original obligation remains a gap.
5. Dispatch the comparison to that same reviewer only when the producer has a dispatchable current packet; a locally blocked packet stays diagnostic while authorized inspection/repair continues. Source-only preparation was not a submission or approval. Retain the first submitted candidate before feedback and freeze its bound context until the response is retained and registered; unrelated work must leave that binding unchanged. Give the reviewer the actual current packet and originals, refreshing relevant source/current-seam bytes changed since preparation. Compare original obligations against criteria, decisions, rules, quantities, recovery, target lifecycles, milestone duties and forecasts. Follow real-provider/recipient proof continuations and every affected target, not just the ones declared in the index. Inspect unmapped and unexamined material, and challenge a plausible wrong implementation. Available material originals still unexamined require further inspection or an explicit unresolved review limit; omission from notes or the ledger does not waive them or justify full-source acceptance. Record actual limits and dissent in one ordinary independently authenticated scope judgment. The source comparison is navigation, not its verdict. For simpler work, a distinct reviewer can compare originals and packet directly. A resumed exposed context is not a fresh blind review; if source-only preparation is needed afresh, use an actual fresh context and preserve the prior provenance. Preserve stale raw dissent after a race; never rebind it or invent independence, and obtain actual review of the corrected candidate.
6. Check the actual result and reviewer identity/context, retain raw output and preparation provenance, then register the exact judgment capture through `ai-prompt-host`. Pass the unmodified envelope back for canonical `record`. Notes have no separate host receipt or acceptance boundary. For newly authored runs configure independent implementation review; assess selected details and relevant source/forecast/authority context in a separate bound implementation judgment. Scope and detail may share a session with separate receipts; historical runs without this duty have no configured detail review. Rejections go to the producer as actual feedback, not coordinator-authored product instructions. The producer repairs the cause and submits a fresh bound packet with `--previous`. Reuse the reviewer for targeted conservation: compare original clause, previous/current acceptance, changed dependencies and downstream consumers, actual proof continuation, affected targets and change/no-change paths. Refresh relevant current bytes, revisit material coverage gaps and preserve prior falsifiers; do not repeat unrelated unchanged inspection or reduce review to old finding IDs. The parent never secretly rewrites the plan to achieve a score. Track preparation, setup, review, repair and intervention; report usage only when measured.
7. Once source review, configured detail review and actual instruction verification pass, the producer uses the existing `work-executable` boundary for each bounded item. Within a real implementation request it continues source-consistent reversible work without repeated permission questions. It retains actual command/consumer outputs, including failure and recovery. The parent registers observations it actually witnessed; producer-written positive summaries alone are insufficient. Actual consumer/semantic and applicable design review precede accepting a proof; release has its separate complete-scope and authority judgment.
8. Preserve honest pending inputs at their consumers. Continue other work only when its own executable boundary passes. A verified no-change inspection does not require mutation authority or a redundant owner decision. An explicit plan/review stop ends at that boundary; lack of live access does not authorize a simulated release. A required owner decision, paid action or live operation cannot be inferred from a reasonable technical default.
9. At handoff retain the exact runnable artifact, sources, host captures, judgments, failures, scope/execution status and next action. State what the parent observed versus what the verifier checked. A cold trial measures the shipped workflow including preparation and coordinator/reviewer cost; assisted repair is not first-pass success. Never claim a new host directory or a narrow test proves platform authentication, general autonomy or token savings.

For planning forecasts, retain source-bound milestones, their useful result/recovery and reforecast trigger, disjoint role estimates and typed producer dependencies. Compare capacity only with its explicitly named milestone, release or all-work scope; show unknown estimates and owner waiting separately. Never infer a committed date from labor sums.
