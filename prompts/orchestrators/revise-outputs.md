# Active-slice Revise Gate

When the user requests only an existing-plan audit, inspect and report without regenerating artifacts, resuming execution or migrating a run, even when a checkpoint exists. For an authorized revision of outcome runs, review the full concise scope ledger plus the bounded active slice; do not require exhaustive tasks for all deferred outcomes. The canonical shared resolver and `validate-delivery.sh` determine applicable scope. Legacy task-schema/phase checks remain in the explicit legacy workflow only.

Run `bash .ai-prompts/scripts/validate-delivery.sh <run-directory> --stage plan` for observations during a read-only audit. When revisions are authorized, fix actual failures without hand-authoring success reports. Review:

- Version 2 has current `planningInputs` bindings for the required `planning-integrity.json` and `review-findings.json` companions and, for runs with persistent data or roles, an `architecture.json` domain contract (entities, access matrix, state machines, URL map, API, provider decisions); see `.ai-prompts/docs/planning-integrity.md`. Preserve version 1 as explicitly legacy/unassessed until authorized migration retains its history. Source/contract changes require affected scope review rather than reused approval.
- Every source requirement, actor, real entry and applicable release duty remains represented; exclusions have authority/provenance and non-waivable duties remain required.
- Original document facts agree, or an explicit conflict/authorized resolution remains visible: AI inclusion/exclusion, feedback target versus formal acceptance window, and commercial milestone/payment-trigger deliverables. Partial or unread sources cannot support full coverage. P0/P1 findings and pending owner decisions block their declared targets/stages; closure needs retained evidence.
- Unknown defaults choose the smallest applicable platforms and capabilities. Safety/reliability are explicit, without a generic feature inventory.
- First proof reaches a valuable result through actual composition and a reachable recovery path. UI plans include composed-screen captures; headless plans name actual consumers and operations.
- Milestones have acceptance defined before implementation, complete capability prerequisites, actual app entry, critical resources, health and first usable/manual MLP delivery. Include operator/recovery/handover obligations. Scope visual review to dependent screens so independent infrastructure is not blocked without a dependency. Variants retain feasible obligation/evidence paths and authorized selection. Required/added origins, risks and effort ranges plus reserve match the capacity envelope; unknown/excess commitment remains provisional or an authorized change request. Each milestone and payment belongs to one release scope; no base-contract payment depends on unapproved or unpriced change-order work.
- Units are cohesive useful multi-file changes with concrete paths, ownership, dependencies, success/recovery checks, target and evidence. No hidden megaslice or per-file ticket explosion.
- Canonical multi-file declarations include changed tests, fixtures, runner/bootstrap configuration and lockfiles. Concrete test paths match the actual runner; integration uses its real isolated environment. Empty scaffold collection never satisfies substantive acceptance. Usable, milestone and release boundaries require actual builds through `.ai-prompts/scripts/build-gate.sh <project-root>` with the corresponding `--boundary usable`, `--boundary milestone` or `--boundary release`; task typechecks are separate.
- Detailed unimplemented content across all locations meets the five-unit/4,000-word pre-proof or eight-unit/6,000-word post-proof budget. Only evidenced accepted history and the bound architecture contract are excluded. Any extension is bounded and reviewed before expansion.
- Authorization distinguishes execution, required checkpoints, scope/design/release authority and independent review. Required owner or reviewer acceptance cannot be self-granted.
- Evidence is current, nonempty, raw, source/target/configuration-bound and digest-verifiable. Review provenance is resolvable through trusted sources; an `owner-attested` record quotes the owner's explicit reply verbatim and covers scope review only. A validator cannot infer visual quality or authenticate a copied session ID.

Challenge copied IDs against actual requested behavior and inspect operator/handover results; schema and keyword checks are not semantic proof. For an authorized revision, regenerate only the affected bounded artifacts after failure; preserve full scope and decision/evidence history. Re-run appropriate gates. Report residual failures honestly and keep plan-ready pending. A plan-ready gate does not establish proof-accepted, slice-accepted or release-ready. At advancement/release use the corresponding validation stage and semantic review against raw behavior.

For legacy `revise-report.md`, let `.ai-prompts/scripts/revise.sh` author the report. Do not claim its task-schema checks validate outcome evidence or release readiness.
