# Greenfield Engine

For new products, use `.ai-prompts/prompts/orchestrators/rolling-delivery.md`. Establish the full outcome/release ledger, then detail the representative proof slice only. The name of this engine is retained for routing compatibility; exhaustive Seed → Features → Tasks expansion is no longer the new-run workflow.

1. Read the brief and verified project context. Name the actual actor/consumer, valuable outcome, entry, target, constraints and unresolved assumptions. Apply entry-point defaults; ask only for material blockers.
2. Create the versioned delivery manifest in an isolated run. Capture all requested scope and applicable baseline duties concisely, including deferred work. Load product vision, architecture, UX, content, research or domain modules only for the slice or a concrete high-risk decision.
3. Design a bounded proof through real composition, with success/recovery acceptance and the evidence/review policy. Use the shared visual/nonvisual budgets; nonvisual work requires no design acceptance. Run stage `plan` and `.ai-prompts/prompts/orchestrators/revise-outputs.md`.
4. Present the scoped plan and proof route. Stop for user-required review; plan-and-implement continues under persisted authorization.
5. Execute, inspect, review and advance via the shared workflow. Do not generate future feature/task files merely to make the full scope look decomposed.

For an architecture-only request produce the requested architecture and source-backed decisions, leaving implementation pending. A design/reference prototype is not evidence that the eventual shipped product works.

Existing legacy greenfield artifacts can continue only through `.ai-prompts/prompts/orchestrators/legacy-workflow.md`; do not rewrite their history or issue outcome-ready claims from legacy completion flags.
