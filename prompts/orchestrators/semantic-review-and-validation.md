# Semantic Review and Validation

Read original requirements before completion narratives. Use `.ai-prompts/prompts/orchestrators/rolling-delivery.md` for canonical provenance, design comparison-v2, evidence currency, impact-scoped reuse, lifecycle and release rules; do not duplicate a second acceptance authority. Existing semantic reports only project findings.

Use the relevant dimensions in `.ai-prompts/prompts/review/`: intent, correctness, composition, adversarial cases, evidence quality, user outcome and content experience. A distinct reviewer independently exercises the actual entry, first useful result and reachable recovery. Inspect composed screens in required contexts; for headless/mixed products exercise the actual consumer, installation or operation. Fake providers cannot prove production integration.

Challenge copied requirement IDs with wrong-behavior examples: a request that never reaches staff, a quote shown to the wrong organization, a retry that duplicates an effect, or a restored database whose files are missing. Compare against original sources, not implementer-selected checks. These examples suggest questions, never add product scope. Also inspect empty states, broken fallbacks, stale screenshots, hidden exclusions and missing operator handover. Schema/keyword success cannot establish semantic fidelity.

Record stable finding ID, source/requirement/outcome/check, expected versus observed behavior, exact target, raw evidence, severity, uncertainty and closure authority. Preserve disagreements; majority votes and review counts never erase blockers. Verify repairs with current post-fix evidence and a valid control.

Before dispatch use `planDeliveryReview` under the shared contract. Reuse unchanged approved judgments, block unchanged rejection, and review changed inputs/new questions only. At release or scope change inspect the whole original brief and cross-role journey. Scope approval, design acceptance, functional acceptance and release review remain distinct; an owner reply cannot substitute for independent review or runtime proof.
