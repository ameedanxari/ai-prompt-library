# Self-maintain

Use the library's own entry point and rolling-delivery contract to improve the library. Select an isolated `prompts/outputs/runs/<run-id>/` run; never overwrite consumer/history output. Preserve all requested maintenance outcomes and applicable packaging/compatibility obligations in the ledger, then implement a bounded representative proof before breadth.

Inspect actual installed-package CLI and TypeScript API behavior, not only prompt wording. Exercise meaningful negative fixtures for budget/scope/evidence/provenance, migration/resumption and release claims. Cover representative UI, headless, native and mixed systems; generated mockups and fake providers do not establish actual target readiness.

Run repository-required behavioral suites, tests, typecheck, build, package/release checks and diff review appropriate to changes. Report exactly which passed and remaining gaps; never write implementation/verification claims before running them. Audit entry, engines, executor, intake, semantic/revise, baseline/module selection, bootstrap steering and human docs together for contradictions. Keep canonical resolver semantics shared across public APIs/wrappers. Do not add a competing writable completion system.

Independent critique must use a distinct reviewer context and actual retained evidence if the declared policy requires it. User acceptance remains owner-reserved. Commit/push follow explicit user authorization and repository policy. Field trials use isolated outputs and preserve application/runtime state until execution is authorized.
