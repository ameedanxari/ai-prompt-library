# Applicable Baseline Checks and Unit Shapes

Baseline topics are obligation checks, not an automatic epic/task inventory. For outcome runs apply this guidance to the full concise ledger and current slice under `.ai-prompts/prompts/orchestrators/rolling-delivery.md`. Use the smallest supported platform set; missing preferences never imply web+iOS+Android, accounts, admin, monetization, localization or theming. Retain applicable safety/legal duties, which cannot be waived by the agent.

## Cohesive units

A unit closes a useful observable outcome/check across its necessary runtime, test, config, documentation, assets and evidence files. Name affected paths and ownership, production consumer, dependencies, precise change, success/recovery acceptance, target and verification. Do not split by artifact kind or file merely to satisfy metadata rules. Separate work where authority, risk, independent dependency or a useful review boundary requires it. Preserve collision detection without forcing one ticket/commit per file.

Phases may describe units within the current slice; they do not require all project foundations before the first product proof. A later slice can introduce necessary foundations. Deferred obligations remain ledger rows until selected; do not create fake tasks for cross-slice dependencies.

## Applicability review

| Topic | Required when applicable |
| --- | --- |
| Identity/roles | Real login/session/recovery and authorization boundaries when accounts or protected roles are required; never infer an admin product from a generic brief |
| Consent/privacy | Actual data inventory, purpose, minimization, retention, rights/export/deletion and consent where relevant; record non-waivable legal duties |
| Safety/security | Threat/failure cases, least privilege, secrets handling, authorization and misuse protection proportionate to domain and target |
| Data integrity | Schema/migration correctness, ownership, representative data and rollback/recovery; production persistence must be exercised |
| Onboarding/content | Useful first value, meaningful fresh/populated/empty/error states and reachable support/fallback; no placeholder copy or fabricated commercial/legal facts |
| Visual experience | Real composed screens, responsive/device states, content hierarchy, accessibility and domain fit; components/tokens alone do not prove acceptance |
| Accessibility | Applicable input, semantics, contrast, focus, assistive technology and usable recovery on actual surfaces |
| Localization/theming | Only requested/applicable locale/theme scope; completeness and composed rendering for that scope, not automatic RTL/dark/white-label products |
| Observability/operations | Useful logs/metrics, ownership, health, provider failure and recovery; privacy-safe evidence and deployment configuration |
| Tests | Meaningful success/failure/integration checks and source/target-bound raw results; tests cannot substitute for actual consumer proof |
| Release/distribution | Actual intended package/deployment/store obligations, signing/permissions, compatible consumer and rollback/support ownership |
| Native | Project/package identity, OS/device/permissions, installed primary/recovery journey and applicable distribution proof |
| Data/ML/AI | Input/evaluation identity, assessed correctness, provenance, declared criteria, failure/adversarial modes and human intervention where needed |
| Infrastructure | Authorized isolated apply or equivalent real operation, reachability/recovery, least privilege, secrets, backup/restore and ownership |
| Documents/media | Render/open/export in intended consumer; substantive accuracy, presentation, compatibility/accessibility and distribution |

Combine profiles for mixed systems. Controlled-provider/fake evidence remains labelled; actual provider integration and release remain unproved. Evidence requirements do not authorize charges, destructive drills or infrastructure applies. Record needed owner decisions and advance independent safe work.

Store screenshot matrices describe required locale/device evidence only for applicable distribution scope. A cohesive capture/review unit may cover that matrix; do not generate one full metadata ticket per frame. Production claims require actual app captures, never generated mockups.

Legacy record schemas are supported through `.ai-prompts/prompts/orchestrators/legacy-workflow.md`; their per-artifact/phase rules must not be imposed on new rolling runs.

For local-only native apps, do not invent an endpoint switcher, remote backend, account, or admin service. Debug/diagnostic actions must use the actual local architecture. Privacy export/deletion can be a native local UI action with evidence over each actual local store / file directory / app-owned cache location. Preserve media permissions, user-controlled deletion, recovery boundaries and honest OS capabilities; storage cleanup is not a system memory optimizer. Apply real OS/device evidence and local fixture isolation.
