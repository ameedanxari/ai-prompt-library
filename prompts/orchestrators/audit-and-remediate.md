# Gap-closure Engine

Use `.ai-prompts/prompts/orchestrators/rolling-delivery.md` for new audits. Preserve the full brief and historical evidence; create an isolated run instead of deleting existing output/application state.

1. Read original requirements and referenced documents before prior completion narratives. Inspect source and the actual target. Reconcile requested actors, journeys, release duties and prior claims with observable behavior. Start at the real public/consumer entry, follow the primary action and reachable fallback/recovery. Report missing, scaffolded, empty, broken or inaccessible states with target/action evidence. Source presence and passing builds do not establish completion.
2. Load `.ai-prompts/prompts/orchestrators/semantic-review-and-validation.md` when challenging completion, reviewing implemented work or deriving remediation. Inspect relevant component/dependency slices, not every historical task by default. Retain known limitations and uncertainties.
3. Establish source-bound lifecycle/data policy and approved reset targets; use pre-launch schema consolidation only with current trusted scope approval and explicit source authority. Live or unknown lifecycle requires conservative compatibility, migration and recovery. Apply the shared lifecycle/reset authority rules. Capture the authoritative full outcome/release ledger in the versioned delivery manifest. Map old task IDs/evidence as historical claims only. Reconcile source-to-outcome completeness and outcome-to-source traceability. Missing current proof remains pending; do not demote or erase original scope to make the audit pass.
4. Detail the smallest representative proof/repair slice that establishes useful entry-to-outcome behavior and its recovery. Before first-proof visual design acceptance use at most two units/1,200 words/9,600 bytes; after design acceptance and before accepted full proof use at most five units/4,000 words/32,000 bytes, as the shared workflow requires. Runtime, tests, assets and config can belong in the same useful multi-file unit. Keep remaining findings concise in the ledger.
5. Run stage `plan` and `.ai-prompts/prompts/orchestrators/revise-outputs.md`. Present the runnable proof route, observed failures, acceptance evidence required, owner decisions and next step. Stop at declared user checkpoints; honor prior execution autonomy within its scope.
6. Execute, inspect, review and advance under the shared rolling-delivery contract. Repair the first useful proof before unrelated breadth; keep missing owner/independent acceptance pending and validate matching manifest/checkpoint state. Never substitute permission to continue for design acceptance or turn review counts into approval.


For explicit continuation of legacy remediation use `.ai-prompts/prompts/orchestrators/legacy-workflow.md`. Invalid or missing manifests in migrated runs must fail closed.

Preserve semantic finding IDs, original requirement IDs and outcome/check lineage when creating remediation units; closure must cite current post-fix evidence, never rename findings away. Prior legacy `gap-list.md` and `remediation-*.md` IDs remain historical references during migration.
