# Executor

Resolve the checkpoint's `run_directory` before loading tasks. For a supported outcome manifest use `.ai-prompts/prompts/orchestrators/rolling-delivery.md`; explicitly selected legacy execution uses `.ai-prompts/prompts/orchestrators/legacy-workflow.md`. Invalid/missing migrated manifests are errors, not legacy fallback.

## Preflight

A request only to review an existing plan remains read-only, regardless of a resumable checkpoint; report findings without regenerating or executing it. For authorized execution, read the current manifest, bounded active slice, authorization, unresolved owner decisions and exact next unit. Run `bash .ai-prompts/scripts/validate-delivery.sh <run-directory> --stage execute`. Version 2 manifests require the digest-bound `planning-integrity.json` and `review-findings.json` companions, plus `architecture.json` for runs with persistent data or roles, through `planningInputs`; read `.ai-prompts/docs/planning-integrity.md` for their compact contract. Preserve explicit legacy/unassessed status for version 1 rather than silently migrating it. Inspect open findings, source conflicts and owner decisions for this target and stage. The execute stage checks plan integrity, scope approval and persisted execution authority before starting construction. Refuse invalid plan/dependencies/budget or missing execution authority. Read original obligations and relevant source locations before derived completion claims; confirm both source-to-outcome completeness and outcome-to-source traceability. Reuse unchanged source context and do not regenerate all future detail. Project/task logs are projections of the authoritative scope resolver, never independent success flags.

For visual work, first implement the smallest rendered representative entry and compare it with digest-bound authoritative design documents. Until first-proof design acceptance, stay within two units/1,200 words/9,600 bytes in one slice; defer dependent screen breadth and the full journey. Keep independent authorized infrastructure unblocked when it has no visual-review dependency, within the same detail budget. Extensions cannot waive this limit. The bound architecture contract is not task detail and is outside these caps. Read the source criteria and required viewport/theme contexts, including phone and desktop for web; tokens/fonts alone do not establish design fidelity.

## Cohesive unit loop

1. Check source/target/dependency changes since planning and invalidate affected evidence/acceptance transitively. Resolve cross-slice dependencies to accepted outcomes with retained current evidence. Technical verification does not substitute for required product acceptance.
2. Confirm the milestone has acceptance defined before implementation and complete prerequisites: actual app entry, critical resources, health, first usable/manual MLP delivery and required operator/handover outcomes. Preserve selected variant obligations and unresolved capacity/change-request duties. Inspect affected paths and ownership before changes; preserve existing work and secrets. Implement the useful change across its necessary files, integration, content and recovery. Follow repository checks and actual runtime contracts. Do not create documentation as a proxy for missing behavior.
3. Run focused meaningful checks after each change and the declared actual entry/action path. Declare changed source, tests, fixtures, configuration, bootstrap and lockfiles together in the multi-file unit. Confirm the runner collects the concrete test paths, with real isolated integration bootstrap before production imports; empty scaffold collection cannot satisfy substantive acceptance. At usable, milestone and release boundaries run `bash .ai-prompts/scripts/build-gate.sh <project-root> --boundary usable`, `--boundary milestone` or `--boundary release` respectively. Each requires an actual production build; cheap task checks/typechecks remain separate. Python production boundaries also require an explicit `--build-command` for the real project build; task `compileall` proves syntax only. Capture source/target-bound raw evidence, including relevant failure/recovery. For visual surfaces capture and inspect the composed application at representative sizes/devices and fresh/populated states. For headless work exercise the real consumer/installed invocation/operational result. Fake fixtures are labelled and leave production duties open.
4. Diagnose failures rather than weakening assertions. `.ai-prompts/scripts/diagnose-harness.sh` and the relevant harness-recovery module can distinguish environment faults from code faults. Bound recovery attempts, preserve failed evidence, and stop when safe recovery/authority is unavailable. Never erase failures to close a unit.
5. Record the observed result and evidence through canonical tooling. For each visual outcome retain `design-review` comparisons of every applicable criterion/context plus comparison-v2 composed-experience judgments per context against current composed entry images for that same outcome; record exact entry route, viewport and theme. Obtain the policy-appropriate trusted `design-review` decision bound by `deliveryDesignReviewBinding`, separately from functional acceptance. Compare intent/materials, composition, hierarchy, content and mobile behavior; record strengths, contrary evidence, rationale and blocking findings; do not substitute token/font, component/palette or navigation approval. A failed/unverified experience remains blocking. Human permission to continue is separate from aesthetic acceptance. Missing, failed or rejected design review requires repair of dependent visual work within the same proof before screen expansion; independent authorized infrastructure continues when it has no visual dependency. Task success establishes only its proved claims. Obtain required owner/independent review with trusted provenance; do not self-author approval or infer it from silence.
6. Run stage `advance` at the slice boundary. Repair failed proof before unrelated breadth. Honor required checkpoints and present the actual runnable target, entry/actions, relevant states, limitations and evidence links. Update manifest and checkpoint together, validate that phase, active slice, next action and bounded reload files match, then present the handoff. Do not hand off mixed old/new state.

Use `.ai-prompts/prompts/orchestrators/semantic-review-and-validation.md` for the acceptance challenge. Compare original source behavior with the implementation, including copied-ID/wrong-behavior negative controls and operator/handover results; requirement IDs and passing keyword checks cannot establish semantic fidelity. Obtain required independent AI review per coherent journey, with a full original-brief/cross-role journey review at release or scope change. Do not restart review without a new question, changed input or unresolved finding; record review input fingerprints and call `planDeliveryReview(scope, kind, outcomeIds, {trustedReviewProvider})` before dispatch. Reuse current authenticated approval, block unchanged authenticated rejection, and dispatch only for `review`; preserve owner/independent duties and never auto-approve at a review-count threshold. Missing required evidence or current source/scope approval blocks dispatch. Default `deliveryReviewBinding` reuses functional acceptance judgment only when outcome `reviewDigest`, plan content and raw semantic observation fingerprints match; fresh exact-target execution remains mandatory. Timestamps/IDs/revisions/candidates alone do not restart that judgment; changed raw outputs do, and must never be silently normalized. Design remains separate, explicit carry-forward evidence bindings pin full immutable old records, and release review always binds exact current records/target fingerprints. At release obtain the separate trusted `release-review` decision using `deliveryReleaseReviewBinding(scope)`, bound to current-candidate execution and original-source artifacts, then run stage `release` for the complete authoritative scope and consistent release candidate. Report incomplete, excluded, owner-blocked and unverified obligations honestly. An unproved required release condition remains open even when local work is useful and complete.

Keep `designAcceptedOutcomeIds` distinct from technical verification, accepted full proof and release readiness. Reuse a visual judgment only when its `reviewDigest` source-criteria/input-dependency fingerprint is unchanged, the original comparison and trusted decision remain available, and fresh current composed entry captures have exact artifact hashes and matching outcome/route/context. Missing or changed-input judgments require review; unchanged rejected judgments remain blocked until reviewed inputs change. Release still needs fresh functional/recovery execution proof. Plan expansion or unrelated edits alone need not restart aesthetic review. Use reviewed outcome `bindingPaths` and target `sharedPaths` for impact; unclassified target bindings affect the full surface. Keep deployment/build IDs in `target.revision`; scope approval binds obligations/path maps while execution/release binds the exact deployment.

Source-bound lifecycle and current trusted scope approval govern schema strategy: authorized pre-launch work may consolidate baseline schemas and use breaking changes without incremental migration history. Live or unknown lifecycle requires conservative compatibility, migration and recovery. Consult `getDeliveryChangePolicy(scope, targetId, {trustedReviewProvider})` or `report.changePolicies[targetId]` for breaking-change, schema-consolidation, reset, migration, compatibility and recovery permissions. The policy performs no operation. Verify explicit authority and actual named disposable target identity before any data wipe; lifecycle/disposable labels alone do not grant it. Preserve evidence history.

## Authorization and changes

Explicit autonomy persists across chats and allows ordinary transitions within scope. Required user checkpoints and owner-reserved design/commercial/legal/safety decisions still stop. Continue independent authorized work while inputs are pending. Evidence requests do not authorize external applies, destructive drills, charges, publishing or paid services.

When a unit uses `commit-task.sh`, record prepared work and retained evidence first, then require a successful commit (or verified recovery of the exact committed tree), and only then advance its checkpoint. A commit-task failure never advances the checkpoint; callers must not mark the unit done before commit success.

Commits follow the user's/repository's policy; there is no mandatory commit per file. Run `.ai-prompts/scripts/safety-check-commit.sh` before any authorized commit and preserve logical reviewable units. Push only when authorized. Never auto-reset a run or consumer state.
