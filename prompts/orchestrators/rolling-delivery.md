# Rolling Outcome Delivery

Shared by Greenfield, Gap-closure and Execute for new runs. Use the canonical versioned manifest/API and `.ai-prompts/docs/delivery-contract.md`; do not invent an alternate writable completion authority. Legacy operation is isolated in `.ai-prompts/prompts/orchestrators/legacy-workflow.md`.

## 1. Establish the full contract

For an authorized new run, create `prompts/outputs/runs/<run-id>/delivery-manifest.json` with `schemaVersion: 2`, required `planning-integrity.json` and `review-findings.json` companions, and manifest `planningInputs` bindings to those project-relative files and their current digests. When the run keeps persistent data or distinct roles, also create the `architecture.json` domain contract before the first integration unit: entities and fields, the role-by-entity access (RLS/grants) matrix, state machines for lifecycle fields, the URL map, the API contract and provider decisions for capabilities the requirements imply (authentication, geocoding, search, email, files). `--stage plan` fails without it. Bind it as a third `planningInputs` entry. These bindings participate in scope approval; update and re-review affected scope when they change. Use `.ai-prompts/docs/planning-integrity.md` for the compact schema. A version 1 run remains explicitly legacy/unassessed for these checks; migration preserves its identity and history and requires authorization. An existing-plan audit stays read-only, even with a checkpoint; do not create, regenerate or migrate its artifacts merely to review them.

Point a root `prompts/outputs/current/resumption-checkpoint.md` to the authorized run with `run_directory`. Bind source inputs to paths and digests. Read original requirements and referenced documents before derived completion narratives; reconcile source-to-outcome coverage and outcome-to-source traceability, retaining all original obligations and unresolved gaps. Capture all explicit requirements, actors/consumers, actual entry points, delivery targets, constraints and highest uncertainties. Reuse verified existing context. Apply `.ai-prompts/docs/planning-quality.md` to the process-inclusive schedule, plain-language owner brief, executable-now summary and evaluation provenance.

In the planning companion, retain the authoritative source inventory, clause dispositions, comparable facts and conflicts before deriving the schedule. Compare scope lists, acceptance terms, payment triggers, dates, prices and deployment commitments across source editions; distinguish feedback targets from formal acceptance. Record partial/unread sources and unresolved owner decisions; no full-corpus claim until inspection. Retain disputed source behaviors explicitly: compare concrete inputs, actions and outputs across editions; preserve each difference with an authorized preserve/equivalent/remove disposition or an unresolved obligation. Retain findings with severity, source bindings, affected targets, blocking stages and closure evidence in the review register. File bindings preserve evidence; trusted scope review establishes decision authority.

Keep a concise ledger of every requested outcome and applicable baseline/release obligation: stable ID and source requirement IDs, observable result, success/recovery check IDs, applicability/reason, target, required evidence, dependencies, release relevance and ownership. Unknowns remain visible. Do not hide detailed implementation in ledger rows. Infer the smallest platform set consistent with the brief; absent preferences do not imply accounts, admin, mobile apps, monetization or unrelated features. Applicable safety/reliability obligations remain required. Non-waivable applicable safety/legal duties cannot be excluded. Keep non-milestone duties off early milestone paths unless required by a source or actual safety dependency; a reviewed manual fulfillment variant preserves the duty. Changing an explicit user requirement needs recorded owner provenance; supported applicability judgments require delegated authority and never erase requested work.

For each operational outcome, name what it reads or mutates, the actual owning target and operator authority. Separate preparation from live-side operations; retain mixed lifecycle obligations in separately owned runs, never a permissive run-wide default or invented external receipt. Record source-bound lifecycle/data/reset policy in `RequirementDocument.lifecycle` and consult `getDeliveryChangePolicy` before schema strategy. Trusted scope approval and explicit source authority may permit pre-launch baseline consolidation; neither permits deletion. New-build status cannot classify existing systems. Reclassify a shipped target before later changes. Unknown/live targets retain compatibility, migrations and recovery; destructive actions require actual target verification and explicit authority. Preserve review/evidence history.

Record authorization separately using the entry point’s defaults: execution permission, required user checkpoints, design-acceptance policy, scope-change authority and independent-review policy. Source requirements, captured evidence and decisions are versioned inputs; eligibility/completion is derived. A model-authored success boolean or accepted-risk row cannot remove a hard obligation.

For every visual surface preserve authoritative written and visual design intent in concise `RequirementDocument.designs` criteria and capture contexts, bound to the original source documents. Require intent, composition, hierarchy and responsive dimensions for each applicable visual outcome, with phone and desktop contexts for web. Declare each criterion’s applicable outcome IDs and source-backed exclusions; exclude valid not-applicable rows from the pass denominator. Retain comparison-v2 judgments of the complete experience per context, including strengths, contrary evidence, rationale and blocking findings. Passing tokens or individual rows cannot override a failed/unverified experience. If no guidance exists, bind and explicitly review a small proposed direction; do not fabricate source authority. See `.ai-prompts/docs/delivery-contract.md` for the canonical comparison record.

## 2. Detail one representative proof

Choose the real entry through the first valuable outcome and reachable recovery path, exposing integration and experience risks. Inspect an existing product's actual primary/recovery actions; do not trust file counts or component approval. First render the smallest representative design against authoritative documents. Scope reviews through explicit dependencies. Until an actually detailed first-proof visual outcome has current trusted composed-design acceptance, retain one slice, at most **two units, 1,200 words and 9,600 bytes** globally; extensions cannot waive it. Afterwards, independent approved/nonvisual work may use **five outcome-level units, 4,000 words and 32,000 bytes** overall, or a current trusted bounded extension. Each still-unapproved visual surface separately retains the two-unit/1,200-word/9,600-byte exploration limit. Count owned task sections and conservatively charge shared/unattributed detail to each pending scope, as `.ai-prompts/docs/delivery-contract.md` specifies. Deferred screens without units do not freeze independent work or earn acceptance. The concise ledger and bound architecture are outside task-detail budgets; task sections inside architecture still count.

A unit is a useful change across its necessary source, test, config, asset and documentation files. Its canonical file declaration includes changed test targets, fixtures, runner/bootstrap configuration and dependency lockfiles; a multi-file unit owns all those paths. Name affected paths and ownership, production consumer/composition, dependencies, concrete change, success and recovery acceptance, verification commands/actions, target, evidence and risks. Do not force a separate ticket/full metadata envelope/commit per file. Do not wrap hundreds of substeps in one unit. Order dependencies within the slice; foundations exist to enable its outcome, not an all-project foundation phase.

Define acceptance before implementing each commercial milestone. Schedule the first usable/manual MLP delivery, actual app entry, critical resources, health checks and evidence producers before the milestones and consumers that need them. Model capability producers/consumers and stage dependencies; verify usable paths through operator setup, recovery and handover. Check the forward path beyond the proof: trace missing input→inspection/work producer→completion decision→consumer; no prerequisite may demand the result it enables. Access/authority gates the producer; completed-result acceptance gates its consumers. Conditional variants must retain feasible requirement/evidence paths before selection and record the authorized selection. Mark required versus added work, inspectable origin reference, risk and rationale explicitly. Bind each milestone and payment to one release scope: the base contract or a named change order (`releaseScopes`). A base-contract payment must never depend on unapproved or unpriced change-order work; give that work its own release train. Compare effort ranges plus integration/review/recovery reserve with capacity; unknown or excessive capacity remains provisional or requires an approved change request.

Select only relevant modules using `.ai-prompts/prompts/orchestrators/module-selection-index.md`. Apply `.ai-prompts/prompts/orchestrators/baseline-task-shapes.md` as applicability/check guidance. Design, implementation, integration, recovery, verification and presentation belong together in the slice. Prototype on the selected production stack at real routes with mock data by default; use reusable existing primitives. A different stack needs an explicit reason (such as an undecided stack), never an automatic disposable rewrite. A prototype can settle design uncertainty; fake-provider/prototype evidence cannot settle production integration or release readiness.

Run `bash .ai-prompts/scripts/validate-delivery.sh <run-directory> --stage plan` and the active-slice revise review. Repair all reported local defects before review dispatch. Batch runtime/test/build bindings and inspect intended-boundary diagnostics before requesting refreshed scope review. Present scope, bounded plan, runnable acceptance route and unresolved owner inputs at the declared checkpoint. Plan-ready grants no proof/release acceptance. Follow persisted execution authorization; if a user planning checkpoint is required, stop. Before construction run `bash .ai-prompts/scripts/validate-delivery.sh <run-directory> --stage execute`, which also requires the current scope approval and execution authority.

A version 2 first-proof slice can explicitly retain `deferredOutcomeIds` while only its representative design and independent prerequisites are detailed. These must be unique applicable outcomes in that same proof with no implementation units yet. Preserve all source requirements, checks and dependencies; refine them into bounded units after the relevant design review. They cannot earn proof/slice acceptance, advancement or release while deferred. Execution readiness applies to the currently detailed units and their real prerequisites; it cannot silently execute deferred work. The existing two-unit pre-design budget is unchanged. Do not relabel a prototype as a completed real-user proof.

## 3. Execute and inspect

Use `.ai-prompts/prompts/orchestrators/executor.md`. Capture raw evidence of the actual built/deployed/installed composition, both useful success and relevant failure/recovery. Inspect composed UI captures for visual surfaces; exercise real consumers/operations for headless surfaces. A build, test fixture, palette sheet or component catalogue alone cannot prove a product journey.

Use the contract’s optional outcome `bindingPaths` and target `sharedPaths` as a reviewed impact map; unclassified target bindings affect the full surface. Keep build/deployment IDs in `target.revision`, separate from stable identity. Scope approval binds original obligations and the path map; execution/release evidence binds the exact deployment.

For early design review capture the actual composed entry for each required viewport/theme, with `capture.route` exactly matching the outcome entry point. Retain `design-review` evidence comparing every applicable criterion/context against a current entry image for that same outcome, with a separate composed-experience judgment per context. Observations must explain how the screen meets or misses source intent, material treatment, hierarchy, content and mobile behavior. Obtain a separate trusted `design-review` decision using `deliveryDesignReviewBinding`; functional approval, token/font approval or human authorization to continue cannot substitute for aesthetic acceptance. A rejection or missing review keeps dependent visual repairs in the same proof and blocks screen expansion; it does not invent a dependency for independent authorized infrastructure. Design review does not prove functional success or recovery.

Functional acceptance judgment may reuse default `deliveryReviewBinding` when outcome `reviewDigest`, plan content and raw semantic observation fingerprints are unchanged; fresh exact-target execution remains required. New timestamps/IDs/deployment revisions/candidates alone do not change the judgment, but changed raw outputs do; never silently normalize them. Design approval stays separate, and release review binds exact current records/target fingerprints and must be fresh. Explicit carry-forward evidence bindings retain full immutable old records.

Every evidence record binds outcome/check, source and dependency snapshot, exact target/configuration/environment/fixture/provider mode, command/action, observed result, time and retained raw artifact with digests. Hash actual composition and dependencies. Reject missing, empty, stale, mismatched or escaping artifacts. Native binds OS/device, SDK consumer/version, data/ML input/evaluation set. Keep production obligations open after controlled-provider proof.

Required reviewers inspect raw outputs and independently exercise the primary result. Bind review decisions to scope/artifact digests and trusted owner message, distinct reviewer-session/tool receipt or verifiable external approval. Resolve provenance; copying a session ID or hashing a model-authored receipt cannot authenticate it. An offline validator lacking access reports provenance unverified and acceptance stays pending. Self-review never satisfies independent review. Slice `acceptanceDecisionIds` can retain cumulative owner and independent receipts; when policy requires both, one role cannot substitute for the other. The singular `acceptanceDecisionId` remains compatible. A single owner's chat approval of original-source scope can be recorded as `owner-attested` scope review: show the owner the prompt from `validate-delivery.sh <run> --scope-binding`, and only after an explicit reply using the exact `approve scope <code>` or `reject scope <code>` command, record that reply verbatim with its timestamp and the scope digest; never paraphrase, infer or reuse a reply for a changed scope. Validate with `--owner-attestation`. Attestation is not authentication: it makes the plan ready and satisfies the owner scope duty only, never independent review, acceptance or release.

Verify actual runner roots and include/exclude rules against concrete planned test files. Separate isolated real integration environments and bootstrap from mocked unit imports. Substantive tests must collect tests; an explicitly labelled empty scaffold cannot establish acceptance. At the first usable delivery, each milestone and release, run `bash .ai-prompts/scripts/build-gate.sh <project-root> --boundary usable`, `--boundary milestone` or `--boundary release` respectively; an actual production build is mandatory. Cheap task checks/typechecks remain distinct. Retain input-bound receipts and operator/consumer results.

Run focused meaningful checks after each change and required independent AI review per coherent journey. Start another review only for a new question, changed input or unresolved finding; record the review input fingerprint and findings. Use `planDeliveryReview(scope, kind, outcomeIds, {trustedReviewProvider})` before dispatch: reuse current authenticated approval, block on unchanged authenticated rejection, and dispatch only for `review`; keep owner/independent duties separate. Missing required evidence or current source/scope approval also blocks dispatch. Diagnose blocked inputs; no review counter grants approval.

Run `bash .ai-prompts/scripts/validate-delivery.sh <run-directory> --stage advance`. Repair a failed first proof before unrelated breadth. Technical verification may unlock related construction while owner acceptance is pending, but cannot bypass the first-proof boundary or mandatory product review.

## 4. Advance in bounded slices

After accepted proof, detail one active and at most one next slice, at most **eight units and 6,000 words total**. Pending outcomes remain concise ledger rows. Count all unimplemented detail regardless of filenames, nesting, appendices, research packets or archive relocation. Exclude completed history only with retained accepted evidence and lifecycle records. During proof refinement, a current trusted independent `unit-completion` review can retire exact canonical task sections after full unit-outcome technical/design proof; other detail still counts. This frees pending-detail capacity, never accepts an outcome or proof. Use `.ai-prompts/docs/delivery-contract.md` for host dispatch and binding APIs. Review cohesion as well as mechanical size. Budget pressure narrows the slice, never drops scope. Extensions require a concrete risk/dependency explanation, bounded revised limits and the declared review before expansion; a new chat is no extension.

When source, contract, dependencies or target configuration changes, invalidate affected acceptance and dependent eligibility transitively; preserve historical receipts. Cross-slice prerequisites resolve to accepted outcomes with retained current evidence, never fake task stubs. Carry-forward needs dependency-scope justification and explicit review. Unrelated harmless changes need not invalidate everything. A later slice may introduce new foundations without reopening every completed phase.

Reuse a visual judgment only when its `reviewDigest` source-criteria/input-dependency fingerprint is unchanged, its original comparison and trusted decision remain available, and fresh current composed entry captures have exact artifact hashes and matching outcome/route/context. Missing or changed-input judgments require review; unchanged rejected judgments remain blocked until reviewed inputs change. Fresh captures establish current composition; they never relabel old captures as current. Plan expansion or unrelated changes alone need not restart aesthetic review. Full visual slice acceptance still requires current design acceptance alongside functional evidence and required acceptance receipts.

At each declared checkpoint show the pass’s user outcome, actual target, success/recovery actions, evidence, limitations and next bounded slice; stop only where required by authorization. Required owner/reviewer absence remains pending while independent authorized work continues. Preserve source and decision history. Update manifest and checkpoint together before handoff; validate that checkpoint phase, active slice, next action and bounded reload files match the authoritative manifest before presenting it.

## 5. Release against full scope

At release and whenever scope changes, independently review the full original brief and cross-role journeys before accepting the derived completion narrative. Reconcile both coverage directions, inspect whether copied requirement IDs claim the wrong behavior, and verify deployment/operator and handover outcomes. Stable IDs and keyword checks cannot prove semantic fidelity. Retain fresh functional/recovery evidence on the release candidate even when a visual judgment is reused. Obtain a trusted `release-review` decision with `deliveryReleaseReviewBinding(scope)`, binding the original-brief/cross-role journey review to current-candidate execution and original-source artifacts; other approvals cannot substitute. Run `bash .ai-prompts/scripts/validate-delivery.sh <run-directory> --stage release` against one consistent release candidate and the authoritative complete obligation set, not an implementer-selected subset of gates. For separately accepted release trains, use the explicit source-bound membership and `--release-scope` contract in `.ai-prompts/docs/planning-integrity.md`; default release remains the full union. Name the boundary in the result. Evaluate security, privacy, safety, data, accessibility, performance, operations and distribution as applicable. Every required outcome needs current evidence and required review. An authorized exclusion is still an exclusion, never success. Empty gates, stale screenshots or fake provider success cannot prove release-ready.

Measure actual prompt words/bytes, unit counts, review rounds and rework. Record token usage only when observed; generated bytes do not establish charged context or guaranteed savings. Report actual validation limits honestly. Do not claim this library beats a plain prompt without measured comparative useful outcomes, coverage, review effort and rework.

Evidence never authorizes an infrastructure apply, destructive drill, financial transaction, paid service, publish or other consequential action. Use authorized disposable targets and stop for missing authority. Never disclose secrets or use production fixtures unsafely.
