# Planning pipeline

Turns a project's documents into a complete, granular development plan, then builds it. It follows the conventional order:

1. Understand the work.
2. Split it into modules.
3. Detail each module.
4. Assemble the roadmap.

Each stage is one prompt. Each stage writes readable markdown under `plan/` in the consumer project. A gap gets a stated default; the pipeline never stops to wait for one. Every stage is judged on one thing first: whether a team building from the plan would deliver what the sources want built.

| Stage | Prompt | Writes |
|---|---|---|
| 1 Inventory | `01-inventory.md` | `plan/01-SOURCES.md` |
| 2 Understand | `02-understand.md` | `plan/02-BRIEF.md` |
| 3 Decompose | `03-decompose.md` | `plan/03-ARCHITECTURE.md`, `plan/03-MODULES.md` |
| 4 Elaborate | `04-elaborate.md` | `plan/modules/<id>.md`, one run per module |
| 5 Integrate | `05-integrate.md` | `plan/05-ROADMAP.md` |
| 6 Critique | `06-critique.md` | `plan/reviews/<stage>.md`, after any stage |
| 7 Implement | `07-implement.md` | Code, tests and roadmap updates, milestone by milestone |

## Running a stage

Give the agent `00-RULES.md`, the stage prompt, and the location of the sources and the `plan/` folder. Run each stage in a fresh context; later stages read earlier outputs rather than relying on conversation memory.

- **Stage 4** runs once per module. Modules can run in parallel: each writes only its own file and lists what it needs from other modules, and stage 5 resolves those lists.
- **Stage 6** is optional, after any stage, by a different agent. The producer fixes critical and major findings in stage order (modules in parallel, then stage 5 again on the existing roadmap), and the reviewer checks the fixes once. What is still open after that is recorded as residual and does not block.
- **Coverage** can run from stage 3 on: `node .ai-prompts/scripts/coverage.mjs plan`. Errors about later stages are expected until those stages have run.

Optional owner checkpoints, about 15 minutes each:

- after stage 2, review the assumption register
- after stage 3, review the module split

The pipeline continues on its defaults if nobody reviews.

## Keeping a plan current

Every file a stage writes starts with a stamp such as `<!-- ai-prompt-library 3.2.0 · stage 2 -->`. `stage-versions.json` records the version in which each stage last changed its output. Run:

```bash
node .ai-prompts/scripts/status.mjs plan
```

It lists each plan file as current, stale, unstamped or missing, and names the earliest stage to re-run. Re-run that stage and every later planning stage in order. A re-run updates the existing files in place: it keeps the IDs of items that still apply, never reuses removed IDs, and keeps progress marks such as done tasks. Re-run a stage the same way when the sources change.

## Gates

- **Coverage check** (`node .ai-prompts/scripts/coverage.mjs plan`): every requirement maps to a module, at least one acceptance criterion and at least one task; no dangling IDs; every task is placed in the roadmap once, after its dependencies. It also totals estimates per module.
- **Status check** (`node .ai-prompts/scripts/status.mjs plan`): the plan was generated by the current version of every stage.
- **Critique**: the stage 6 checklist, judged against the sources.
- **Tests and CI** during implementation: every acceptance criterion becomes an automated test where feasible.
