# State and operations

For the active journey, inspect current accessible state ownership: entities/fields, routes and interfaces, configuration, who may read or mutate, and lifecycle transitions. Distinguish reported behavior, observed code/runtime and adopted intent. Retain relevant file/locator bindings and refresh changed bytes before relying on them in detail or repair review. Check the same rule across UI, API and storage policy; a correct narrative cannot repair a contradictory access matrix. Exercise at least one denied action across roles or tenants where that boundary exists.

Follow an effect through retries and failures. What identifies an operation? Where is durable intent recorded? When is it acknowledged? What happens after timeout, restart, duplicate delivery, out-of-order input or a partial write? A scheduler declaration alone does not explain dispatch, missed ticks, concurrency, retry or replay. For ambiguous email/payment/provider results, reconcile through supported identifiers/status before retrying. Promise exactly-once effects only when the actual boundary supports the claim.

During planning, compare the selected trigger and handler contracts end to end, including supported request method, authentication, scheduling, retry and provider limits where relevant. Resolve available public facts from current primary sources before scope review. If contracts differ, retain a supported adapter preserving adopted intent or the specific unresolved material capability; do not defer discovery merely because implementation is later, infer account access, or silently change the provider.

Read each operation's success and recovery prose against every affected target, not just its declared IDs. Local artifacts, new disposable deployment, retained application/data, routing and existing host content have different lifecycles, operators and authority. Bind actual effects to the corresponding work targets, inputs and target-bound acceptance/release closure. A planning document cannot own proof of live cutover. Unknown/live data needs compatibility, migration and recovery until verified authority permits otherwise; an approved plan never authorizes deletion or production mutation.

Split preparation, live read, deployment, sending, data mutation and decommission where one action cannot describe the effects honestly. Recovery must name its affected retained targets too. Unknown access/identity blocks the operation needing it, not independent authorized preparation. A read-only verified-no-change branch does not require live mutation authority or a redundant owner decision; a correction still needs its actual decision and grant. In new runs `declared-targets` consistency rejects a declared local write to a live or production target during planning, without demanding future grants merely to plan correctly classified work. It cannot infer missing targets/effects from prose: the original-source reviewer checks both. Execution still requires actual authority; unsupported retained deletion stays blocked rather than being reclassified as disposable work.

Test recovery against the resources actually used: database plus files, queues, secrets/configuration and dependent providers as applicable. Restoring one component does not establish a restored service. Inspect stale clients, rollback compatibility, replay and operator handover. Use isolated fixtures and authorized disposable environments; keep secrets and real personal data out of retained evidence.

For native work verify the OS capability/permission boundary on the actual supported device/runtime. Product names do not create privileged capabilities: app-owned cache cleanup differs from arbitrary system memory control. Reflect unsupported behavior honestly and test permission denial, cancellation and recoverable interruption.
