# Consumer proof and recovery

Choose the real consumer: user route, installed command, SDK caller, API client, artifact reader or operator procedure. Exercise entry/setup → useful result → reachable failure/recovery on the actual composition. Start from current inspected routes, state and interfaces, not a historical walkthrough. A test importing a mocked module cannot prove installation, provider integration or operations. Keep controlled-provider evidence labelled and retain real-integration obligations.

During planning, follow any claim that an external effect is proved separately to its actual canonical work, criterion, target and release closure. Does that continuation cover this provider/session, recipient, authorized effect and recovery? Another feature using the same vendor or an unlinked future work label is insufficient. If absent, retain the missing delivered acceptance and its future access/capability/authority input now while deferring executable detail. An authorized controlled recipient can establish real delivery; suppressing the sender, copying a token or substituting a deterministic response cannot. Keep rehearsal/staging separate from required delivered behavior, without inferring live access or permission to purchase it.

Make checks executable before claiming them. Confirm runner roots, includes/excludes, actual test file ownership, fixture/bootstrap configuration and required resources. Substantive suites must collect tests. Retain the command, exit status, actual collected counts and raw results; do not relabel plain output as JUnit or fabricate passing counters. Required build/package checks must run the product's real production build, not merely a syntax/typecheck substitute.

At an inspected implementation or runtime seam, challenge the source-valid side of a broad input or state promise and pair it with a nearby invalid control. Use valid controls and one-defect negatives so a failure demonstrates the intended boundary. Test semantic wrong behavior while retaining IDs: wrong recipient, wrong tenant, duplicated effect, missing restored files or an operation that never reaches its consumer. Structural validation cannot discover omitted source meaning by itself.

When a harness fails, inspect its actual logs/artifacts and distinguish infrastructure failure from a product/test defect. For port conflicts choose an isolated configured port; for a corrupted tool cache invalidate only that cache. Reinstall heavy browser/runtime dependencies only when the diagnosed failure needs it. Do not delete all dependencies as a routine retry. A snapshot mismatch requires judgment about the expected result rather than automatic acceptance. Repeated unchanged failures need a new diagnosis, not a longer retry loop.

Retain honest missing, failed and unrun checks. Fix the cause instead of weakening assertions. During repair compare original, previous and current acceptance and inspect affected current implementation bytes, proof continuations, downstream consumers and change/no-change recovery. Preserve earlier wrong-behavior counterexamples; closing findings or retaining the same IDs does not establish conservation. At handoff include setup/actions, observed outputs, raw evidence, limits and next unblocker. Release proof covers the complete selected original scope, the current candidate and operator/handover obligations.

For owner-facing plans, retain concise source-derived amounts, payment or milestone triggers, feedback versus acceptance, decision-by points, affected work and explicit unknowns in canonical owner summaries and decision descriptions. Compare the brief with original commercial sources, not only the populated summaries; an omitted term remains a finding. A proposed effort estimate does not narrow required scope, and an actual source budget remains a visible constraint. In the source comparison, inspect missing producer work and existing evidence separately; neither alone proves acceptance.

For an explicitly source-justified physical-operation target, do not invent a software build. Inspect the actual operation, recovery, target and authority, and challenge an exemption that conceals software delivery. Any software target in the same release still needs its own real build evidence. An exemption is a reviewed source claim, not execution permission.
