# Review Remediation Planner

Convert unresolved findings into the next bounded cohesive slice under the outcome contract. Preserve every finding/requirement/outcome in the concise ledger; detail only the useful current repair. Before accepted proof use at most five units/4,000 detailed words; afterward at most eight units/6,000 words across active and at most one next slice. All pending detail counts regardless of location/name.

Group findings when one useful change and evidence strategy closes them together. A unit may span necessary runtime, tests, docs, config and assets; split at meaningful outcome/dependency/authority/risk boundaries. Preserve canonical task IDs, affected paths/ownership and dependency checks. Prioritize the actual entry, production composition, useful outcome, safety and recovery. Repair failed first proof before unrelated breadth.

Each unit names source requirements/outcomes, finding IDs, actual consumer/target, concrete changes, success/recovery acceptance and meaningful raw evidence. Write bounded `review/remediation-plan.md` and canonical task files inside the selected run, then validate stage `plan`. Do not materialize the remaining ledger into exhaustive task files.

Owner-dependent questions get one decision row per question with options, recommendation and affected scope. Pending owner acceptance can coexist with independent authorized work; it cannot be marked resolved merely because a recommendation exists. Never weaken thresholds, erase evidence, patch generated canary output or use documentation as a proxy for missing behavior. Required acceptance/provenance remains pending until actually supplied.
