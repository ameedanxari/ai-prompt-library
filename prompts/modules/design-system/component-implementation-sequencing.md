# Component Implementation Sequencing

## Purpose

Build only the reusable tokens/components needed for the active representative proof, alongside its composed screens. Avoid an exhaustive all-project design-system foundation phase.

## Instructions

Inspect existing components/tokens and actual visual references. Extend their semantics for the slice, preserve accessibility and shared ownership, and integrate them through the real entry-to-value journey. A cohesive multi-file unit can include components, screens, content and tests. Order genuine dependencies within the slice; do not force a metadata ticket/commit per component or file.

## Examples

For a booking proof, build the needed button/form/error patterns together with the reachable booking screen and recovery route, then inspect actual captures on the declared target. Later slices may add components as needed. A palette/catalogue review supports design discussion but cannot accept the composed application.

## Acceptance

Require actual composed-screen success/recovery captures, useful content and interaction/accessibility checks. Follow the manifest's owner/independent review policy and trusted provenance; no self-granted approval or global screen-work block from generic module text.
