# Delivery contract

New delivery runs use `schemaVersion: 2`, `kind: outcome-delivery` in an isolated `prompts/outputs/runs/<run-id>/delivery-manifest.json`. The canonical schema is `.ai-prompts/src/delivery/types.ts`; package APIs and shell wrappers share its resolver. This guide describes behavior, not a second schema or completion authority.

The root `prompts/outputs/current/resumption-checkpoint.md` selects a run via `run_directory`. Resolve/confine the directory before reading tasks. A missing manifest after migration or an unknown/invalid schema fails closed. Explicit legacy operation can continue old records but cannot produce an outcome-verified release claim.

The manifest includes `runId`, `scopeRevision`, `projectRoot`, `sourceInputs`, `surfaces`, `authorization`, `planningBudget`, `outcomes`, `slices`, `activeSlice`, `firstProofSlice`, optional `nextSlice`, `evidenceRefs`, `decisionRefs` and optional `releaseCandidate`. Source-input JSON documents retain original-source path/digest bindings and authoritative requirement records, so an implementer cannot invent a smaller set of release gates. Read the original brief, referenced documents and applicable obligations before derived completion narratives. Reconcile both source-to-outcome coverage (every obligation retained) and outcome-to-source traceability (every claimed outcome justified); preserve source locations, uncertainty and unresolved work. Outcome IDs map back to those requirements; source and decision history remain versioned inputs.

For visual surfaces, requirement documents also contain `designs[]`: `surfaceId`, `sourceRefs`, `criteria[]` (`id`, `dimension`, `sourceRef`, `sourceLocation`, `expectation`, `applicability`) and `contexts[]` (`id`, pixel `viewport` such as `390x844`, `theme` such as `light`). Dimensions are `intent`, `composition`, `hierarchy`, `responsive`, `typography`, `imagery` and `interaction`; the first four must apply to every applicable visual outcome. Each criterion declares `applicability: {outcomeIds, exclusions: [{outcomeId, sourceRef, sourceLocation, reason}]}`; every surface outcome is covered or explicitly excluded with source-backed reasoning. A dimension may be omitted for an outcome only where allowed; core intent/composition/hierarchy/responsive coverage cannot be excluded. Web contexts include phone and desktop. Bind all authoritative original design documents by digest and preserve concise source locations/expectations, including written intent. If none exist, author a small proposed direction, bind it as an original source and explicitly review it without fabricating owner authority.

Existing runs missing the required applicability or comparison-v2 contract fail closed and require explicit migration. Preserve historical evidence and decisions, update source contracts deliberately and obtain fresh required review; never relabel generic, incomplete or rejected receipts as design acceptance. Do not silently downgrade evidence requirements or migrate a consumer run merely because the library was updated.

Targets identify environment, provider mode, real bindings and stable surface-specific identity: native OS/device, SDK consumer/version, data/ML input/evaluation set. Store changing deployment/build identifiers in optional `target.revision`, separate from stable `identity`. Optional outcome `bindingPaths` and target `sharedPaths` form a reviewed impact map: shared bindings affect every surface outcome; explicitly mapped bindings affect their outcomes and dependents; unclassified target bindings conservatively affect the full surface. Scope approval binds source obligations and this path map, not runtime file hashes or deployment revision. Exact execution/release evidence still binds the actual deployment. Outcomes identify actor, actual entry, surface, applicability/reason, success/recovery check IDs, evidence kinds, release relevance and technical/accepted dependencies. Exclusions retain scope and decision provenance; non-waivable applicable safety/legal duties stay required. Changing an explicit requirement needs owner authority.

Each slice contains outcome-level cohesive units and every detailed file. Unit IDs match canonical task IDs such as `tasks-proof.md#T1`; existing task metadata/parser checks still apply. A useful unit can own necessary source, test, config, docs and assets across multiple paths. Preserve `filePaths`/affected-path ownership rather than forcing per-file task envelopes or commits. Use parser-supported multi-path metadata; do not invent a replacement task syntax.

A version 2 first proof slice may retain a unique `deferredOutcomeIds` subset of its applicable `outcomeIds` while rendering the representative design. Retain each deferred outcome's complete source requirements, success/recovery checks and dependencies; give it no implementation unit until refinement. The detailed units cover every non-deferred slice outcome. Plan validation still considers the full ledger; execution scopes review blockers and prerequisite readiness to the detailed units and their actual dependencies, so an unrelated future UI decision cannot block independent authorized foundation work. Defer detail within this same proof, never manufacture a separately accepted prototype proof or drop manual MLP obligations. After visual acceptance add bounded journey units and remove the corresponding deferrals. Any remaining deferral prevents slice/proof acceptance, advance and release, even when evidence or acceptance metadata claims success. It does not extend the pending-detail budget.

Before the first proof's visual outcomes have current design acceptance, the pending-detail cap is one slice, two units, 1,200 words and 9,600 bytes; extensions cannot waive it. Render and review the representative entry before detailing backend breadth or the full journey. After design acceptance and before accepted full proof the cap is one slice, five units, 4,000 words and 32,000 bytes. After full proof it is one active plus at most one next slice, eight units, 6,000 words and 48,000 bytes total. Rejected or missing design review keeps repairs in the same proof before unrelated breadth. Corpus scan roots must cover every pending detailed document regardless of location/name; ledger files stay concise. Accepted completed history is excluded only with retained lifecycle/evidence proof. Bounded reviewed extensions need concrete dependency/risk reasons before expansion. Mechanical size checks complement human cohesion review; a thousand-step unit is not acceptable.

Authorization records execution, checkpoints (`every-slice` or `autonomous`), design acceptance (`owner`, `independent` or `agent`), scope-change authority and independent-review requirements plus implementer context. Record the trusted user instruction behind the selected policy. Ordinary autonomy persists across chats; owner-reserved acceptance and required user checkpoints remain binding.

Evidence binds outcome/check, exact target/snapshot digests, command, observed result/time, raw nonempty artifact path/digest and production-composition status. UI image captures identify the actual composed entry/success/recovery state and viewport. Controlled/fake-provider proof retains production-integration duties. Relevant source/configuration/dependency changes stale affected acceptance transitively. Reuse needs explicit reviewed dependency scope; absent a complete impact classification, use the conservative full-surface boundary. Release evidence must identify one consistent candidate.

Evidence kind `design-review` retains JSON `schemaVersion: 2` with `comparisons` and `experience`. Comparison rows contain `criterionId`, `contextId`, `imageEvidenceId`, `observation` and `result` (`pass`, `fail`, `not-applicable` or `unverified`). Cover applicable criteria for the same outcome/context using composed entry captures; `capture.route` exactly equals its entry point with matching viewport/theme. `not-applicable` is valid only for a source-backed criterion exclusion and is excluded from the pass denominator; missing or unverified applicable rows never pass.

Every required context also has an `experience` judgment: `{contextId, imageEvidenceId, result: pass|fail|unverified, observedStrengths: string[], contraryEvidence: string[], rationale, blockingFindings: string[]}`. Inspect the actual composed experience against source intent, material treatment, composition, hierarchy, content and responsive behavior. Record contrary evidence and blocking findings even when individual tokens/criteria pass. Failed/unverified experience blocks design acceptance. A separate policy-appropriate trusted `design-review` decision uses `deliveryDesignReviewBinding(scope, outcomeIds)`; human authorization to continue is distinct from aesthetic acceptance. `designAcceptedOutcomeIds` remains distinct from functional proof and release.

A visual judgment may be reused only with unchanged `reviewDigest`, a stable fingerprint of its source criteria and input dependencies, and the original comparison plus trusted decision retained. Supply fresh current composed entry captures with exact artifact hashes and matching outcome/route/context; missing, rejected or changed-input judgments cannot be reused. Plan expansion or unrelated runtime edits alone need not trigger a new aesthetic judgment. This reuse never replaces fresh functional/recovery and release-candidate execution evidence.

Decisions bind scope/artifact digests, reviewer identity/context/role, result and trusted provenance. Default `deliveryReviewBinding(scope, outcomeIds)` binds outcome `reviewDigest`, plan content and semantic observation fingerprints: raw artifact SHA, outcome/check/kind, command, observed result/result, capture, consumer and production composition. Fresh exact-target execution remains mandatory, while unchanged raw results may retain the functional acceptance judgment across new timestamps, evidence IDs, deployment revisions or candidates. Do not silently normalize outputs to manufacture equality; design approval remains a separate gate. Passing an explicit third evidence argument for carry-forward instead pins the full immutable old records. `deliveryReleaseReviewBinding(scope)` always binds exact current full records and execution-target fingerprints, plus original-source artifacts, so release requires fresh review. A copied session ID or hashed agent-written receipt cannot authenticate acceptance. A trusted host can supply a review-verifier module outside the project through the CLI's `--review-verifier` option; it must resolve the original trusted owner/reviewer/external receipt and verify actor, context and bindings. The implementer must never write a verifier that simply returns true. Without trusted provenance access, acceptance remains unverified/pending; plan integrity alone can still be assessed.

**Owner-attested scope review.** A single-owner project often approves scope in chat, which no host can authenticate. Record that approval as provenance `owner-attested`, a level distinct from authenticated review:

1. Run `validate-delivery.sh <run> --scope-binding`. It prints the scope-review binding (`scopeDigest`, `outcomeIds`, `artifactDigests`) and a confirmation prompt containing an 8-character code from the scope digest.
2. Show the owner the prompt and wait. Record nothing unless the owner explicitly replies with the exact command `approve scope <code>` (for example `approve scope 3f9a1c2b`), or `reject scope <code>` for rejection. Surrounding whitespace, case and one trailing period/exclamation mark are ignored; conditions, questions and longer prose are not interpreted as approval.
3. Append a `scope-review` decision with `reviewer.role: owner`, the binding, and `provenance: {kind: 'owner-attested', reference, attestation: {quote, messageAt, scopeDigest}}`. `quote` is the owner's reply verbatim and `messageAt` its timestamp. `createOwnerAttestedScopeReview(scope, …)` builds the record and refuses one that does not confirm the current scope.
4. Validate with `--owner-attestation` (shell wrappers: `AI_PROMPT_OWNER_ATTESTATION=1`). This uses the library's reference adapter, `ownerAttestationProvider`, which is also importable for host composition. It returns true only for complete owner-attested scope reviews whose attested digest, outcomes and artifacts match the current binding, whose quote is present and repeats the code, and whose timestamp is not in the future. It verifies nothing else.

The validator applies the same structural checks whatever verifier is supplied. An owner attestation can satisfy only the owner (or agent) duty of a `scope-review`, never an independent duty, acceptance, design, release, scope-change or budget decision. At `--stage plan`, a valid attestation makes the plan ready even when the policy also requires independent scope review. `execute` and later stages still need every required role, so an independent duty still needs an authenticated receipt. An attested rejection blocks like any other rejection. Any scope change alters the digest, so the old attestation stops applying and the owner must confirm again. Reports state the level in `scopeReview: {approved, provenance: authenticated|owner-attested|none, missingRoles}`. The attestation proves a complete record bound to this exact scope; it cannot prove who typed the quote. Never paraphrase, infer or reuse a reply.

Run from the consumer project root:

```bash
bash .ai-prompts/scripts/validate-delivery.sh prompts/outputs/runs/example --stage plan
bash .ai-prompts/scripts/validate-delivery.sh prompts/outputs/runs/example --stage execute
bash .ai-prompts/scripts/validate-delivery.sh prompts/outputs/runs/example --stage advance
bash .ai-prompts/scripts/validate-delivery.sh prompts/outputs/runs/example --stage release
```

Replace `example` with the actual selected run. `plan` checks bounded executable scope. `execute` additionally enforces execution authorization and current scope approval before construction. `advance` requires current proof/acceptance for eligible transitions. `release` evaluates the authoritative full obligation set and current release-candidate evidence. It requires a trusted `release-review` decision using `deliveryReleaseReviewBinding(scope)`, covering the original brief and cross-role journeys and bound to current-candidate execution plus original-source artifacts; scope/design/slice approval cannot substitute. Read actual failures; never turn a passing schema/build into product acceptance. Plan-ready, proof-accepted, slice-accepted and release-ready remain distinct derived decisions. Task contracts, completion reports and logs project this state.

Actual visual surfaces require captured composed screens and human/reviewer inspection; nonvisual work requires real consumer/operational evidence. Mixed systems combine profiles. Evidence gates do not authorize applies, destructive drills, charges, publishing or other consequential actions. Use authorized disposable targets and preserve pending owner inputs while pursuing independent local work.

Mechanical design checks establish comparison coverage, image context, freshness and trusted provenance, not aesthetic quality. Reviewers must read the authoritative documents and judge actual composition against them; tokens/fonts, navigation and generic screenshots alone cannot establish fidelity.

Run focused checks after each meaningful change, independent AI review per coherent journey when required, and full original-brief/cross-role journey review at release or scope change. Start a new review only for a new question, changed input or unresolved finding; record its input fingerprint and findings. Use `planDeliveryReview(scope, kind, outcomeIds, {trustedReviewProvider})` before dispatch (`kind`: `scope-review`, `design-review`, `acceptance` or `release-review`; result includes `action`, `binding`, `decisionIds`, `missingRoles` and `reason`): a current authenticated approval returns `reuse`, an unchanged authenticated rejection returns `blocked`, and only `review` permits dispatch. Missing required evidence or current source/scope approval also blocks dispatch. Role requirements come from `requiredReviewRoles`; preserve separate owner/independent duties and inspect `missingRoles`. No counter threshold converts failure into approval. Measure prompt words/bytes, unit counts, review rounds and rework. Report tokens only when observed; byte estimates do not prove charged usage or fixed savings. Behavioral tests, installed-package checks and field validation determine what the implementation actually supports.

A slice may use `acceptanceDecisionIds` for cumulative approval receipts; the singular `acceptanceDecisionId` remains compatible. When policy requires owner design acceptance and independent review, both duties must be satisfied by appropriate trusted receipts bound to the reviewed artifacts/scope. One role's receipt cannot silently substitute for the other. Relevant unit/slice content changes invalidate slice acceptance. Original-source coverage approval remains separate from implementation-plan review.

Use repeated `**File:**` fields or a pipe-separated list (for example `src/handler.ts | tests/handler.test.ts`) for cohesive units spanning files. Task requirement IDs must exactly match the union referenced by the unit outcomes; task dependencies and normalized affected paths must match the manifest.

`--project` emits the active task contract, path ledger and delivery order. These derived reports are exempt from the pending-detail budget only when their complete bytes match canonical regeneration; edits or extra instructions are rejected. Reports do not grant execution or acceptance.

Evidence captured with `targetContextDigest` can be carried forward after harmless source changes only with its original authenticated acceptance, an explicit fresh `carry-forward` decision naming `evidenceIds`, and fresh current slice acceptance. The original observation record and artifact remain immutable. Target environment, provider, identity, revision, or production/release attribution cannot be upgraded through carry-forward; changed target context needs new execution evidence. Visual judgment reuse follows the separate `reviewDigest` and fresh-capture rule above; it does not carry an old screenshot forward as current evidence.

Before handoff, update the manifest and checkpoint as one logical operation: validate the selected run, then write a checkpoint whose phase, active slice, next action and reload files match the manifest. Revalidate the checkpoint before presenting it; never hand off mixed old/new state.

Lifecycle is source-bound in `RequirementDocument.lifecycle`: `{stage: pre-launch|live, dataPolicy: disposable|retain, sourceRef, sourceLocation, resetTargetIds: string[]}`. With explicit source authority and current trusted scope approval, pre-launch work may consolidate the baseline schema, make breaking changes and omit incremental migration history. Live work requires compatibility, migration and recovery planning. Missing/unknown lifecycle is conservative. A disposable label never authorizes a wipe: verify explicit reset authority and the named disposable target; retain other data. This product-schema policy does not permit erasing review/evidence history or silently migrating delivery contracts.

Use `getDeliveryChangePolicy(scope, targetId, {trustedReviewProvider})` before choosing schema/reset strategy; validation reports the same policy in `changePolicies[targetId]`: `stage`, `allowBreakingChanges`, `allowSchemaConsolidation`, `allowDataReset`, `requireMigrations`, `requireCompatibility` and `requireRecovery`. This is a policy result, not a data operation. The caller must verify the actual reset target identity and explicit authorization before executing a permitted reset.

For functional judgment reuse, retain the original full reviewed evidence records unchanged. Match separately retained current observations by semantic result and raw artifact digest, then bind the judgment to the original records. New-target observations must be newer than the retained originals; rewriting their target labels or timestamps invalidates the signed judgment. Final release review pins the current full records.

## Planning integrity and compatibility

New manifests use `schemaVersion: 2` and require `planning-integrity.json` and `review-findings.json` alongside the manifest, plus `architecture.json` when the run keeps persistent data or roles. See [planning integrity](planning-integrity.md). The same read-only validator feeds the public delivery API and legacy readiness wrapper. Findings block only applicable targets/stages; project-wide readiness considers every target. Malformed or stale registers fail closed. Plan review may be complete while execution remains blocked by owner/commercial inputs.

Version 1 remains readable with its previous outcome checks and is reported as unassessed for missing planning integrity. It does not inherit version 2 assurance. Migration is explicit: preserve the prior run and IDs, add source dispositions/prerequisites/evidence/capacity and current reviews, then update the manifest version. Never invent approvals or change active granularity while migrating.

## Release trains at runtime

When a version 2 planning contract declares separate release trains, an optional `releaseScopeId` on every original requirement and outcome establishes complete reviewed membership. `*` marks shared non-waivable required duties. Named release validation (`--stage release --release-scope R1`) checks R1, shared duties and recursive dependencies while leaving unrelated R2 obligations visible and pending. Without a selector the full-union release remains required. See [planning integrity](planning-integrity.md#named-runtime-release-boundaries) for exact authoring rules.

The selected train is part of `deliveryReleaseReviewBinding` and its trusted release-review decision. Scope review always covers the complete original ledger. Never reinterpret an R1 success as full-product completion; record the selected boundary in the report. Unmapped legacy runs support only union release. Partial mappings, unknown trains, mixed-train slices and unapproved/unpriced change-order release are errors, not scope exclusions.
